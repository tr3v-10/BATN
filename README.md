# Payments with PayHero

JADILI keeps the mock provider for offline demos and can use PayHero to send M-Pesa STK Push prompts.

## Provider selection

Set `PAYMENT_PROVIDER=mock` for local demos (default), or `PAYMENT_PROVIDER=payhero` for PayHero. Never put provider credentials in frontend variables.

Copy `.env.example` to `.env` and configure:

- `PAYHERO_API_USERNAME` and `PAYHERO_API_PASSWORD`: PayHero API credentials.
- `PAYHERO_CHANNEL_ID`: the channel ID shown in PayHero under Payment Channels > My Payment Channels.
- `PAYHERO_BASE_URL`: normally `https://backend.payhero.co.ke`.
- `PUBLIC_BASE_URL`: public HTTPS base URL of this backend (no trailing slash).
- `PAYHERO_CALLBACK_SECRET`: a long random secret used in the callback URL path.
- `PAYMENT_PROVIDER`: `mock` or `payhero`.

PayHero uses HTTP Basic authentication. The backend constructs the token from the API username and password. Do not commit `.env`, expose credentials in Vite variables, or log authorization headers.

## Run locally

From `backend/`:

```sh
npm install
npm start
```

From `frontend/` in another terminal:

```sh
npm install
npm run dev
```

Set `VITE_API_BASE_URL=http://localhost:5000` in the frontend environment if the API is not on the default local address.

## Public callback tunnel

PayHero must be able to reach the callback over public HTTPS. Run the backend locally on port 5000, then expose it using one of:

```sh
ngrok http 5000
```

or

```sh
cloudflared tunnel --url http://localhost:5000
```

Set `PUBLIC_BASE_URL` to the HTTPS URL printed by the tunnel, restart the backend, and keep the tunnel running while testing. The callback path is generated by the backend as `/api/payments/callback/<PAYHERO_CALLBACK_SECRET>`.

## Payment flow and reconciliation

Only negotiations in `accepted` state with a final price, clear risk review, and no outstanding mandate approval can be paid. Payment creation is idempotent per negotiation. The backend stores a masked phone number, provider reference, checkout request ID, receipt, state changes, callback events, audit records, and transaction tracking.

A background reconciliation job runs every minute. It checks initiated/processing payments that have been waiting for at least two minutes. After ten minutes without a terminal provider result, the payment is marked failed with `Timed out waiting for M-Pesa`. Before trying again after an ambiguous timeout, check the PayHero transaction status and the customer's M-Pesa messages; do not assume the customer was not charged.

The callback URL includes a secret path segment. Callback amounts and external references are checked, and successful callbacks are confirmed against PayHero's transaction-status endpoint before the system marks a payment paid. PayHero's published callback example documents `Status: Success` with `ResultCode: 0`; its status endpoint documents `QUEUED`, `SUCCESS`, and `FAILED`. Unrecognised statuses are not treated as paid.

## Testing checklist

1. Start with `PAYMENT_PROVIDER=mock` and verify the dashboard and payment history.
2. Run backend tests with `npm test`.
3. For PayHero, obtain API credentials and the correct channel ID from the PayHero dashboard.
4. Use a public HTTPS tunnel and verify PayHero can reach the callback route.
5. Use PayHero's test credits/sandbox facilities if enabled for your account.
6. Before any real transaction, test with **KES 1 to your own personal M-Pesa number**.
7. Confirm the receipt in PayHero and the customer's M-Pesa message before testing larger amounts.

## Known limitations

- PayHero's documented status lookup values are `QUEUED`, `SUCCESS`, and `FAILED`. The callback example documents `Success` and `ResultCode: 0`; a complete cancellation result contract is not published in the pages checked. Unknown callback values are logged and left unchanged.
- The verified API pages did not establish a server-side cancellation endpoint, so the cancel route returns an unsupported response rather than pretending to cancel a live prompt.
- The current application does not expose an owner-mandate approval action. Deals whose mandates require approval remain blocked from payment until that separate approval workflow exists.
- The migration retains the existing one-row-per-negotiation payment intent and records retries as distinct attempt numbers/events. This preserves the existing transaction tracking relationship.
